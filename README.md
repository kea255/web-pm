# Менеджер паролей

Небольшой личный web менеджер паролей с возможностью работы оффлайн.
Интерфейс две панели, категории и записи, у записи можно сменить категорию простым перетаскиванием.
Категории и записи можно сортировать перетаскиванием.
При удалении записи она сначала помечается удаленной, меняет цвет и уезжает в самый низ списка, её можно восстановить или удалить уже из базы полностью.
Встроен простой генератор запоминающихся паролей(omgopass) позволяет сгенерировать пароль при создании записи.

## Структура

```
config.php     	       — константы dbhost / dbuser / dbpass / dbname для DBi
lib/dbi.class.php      — копия библиотеки DBi (MIT), чтобы работать без composer
schema.sql             — схема таблиц users, categories, entries
install.php            — создаёт базу и таблицы
api.php                — JSON API
index.htm              — HTML-оболочка: категории слева, таблица справа
assets/app.css         — стили
assets/app.js          — AJAX, WebCrypto (PBKDF2 + AES-GCM), кэш IndexedDB
assets/omgopass.js     - простой генератор запоминающихся паролей
assets/fontawesome/    — Font Awesome 6: subset (css/fa-solid.min.css ~2 КБ + webfonts/fa-solid-900.woff2 ~158 КБ)
sw.js                  — service worker: кэш оболочки для офлайн-загрузки страницы
```

## Установка

1. PHP ≥ 7.3 с расширением `mysqli`, MySQL или MariaDB.
2. В `config.php` укажите `dbhost`, `dbuser`, `dbpass`, `dbname`.
3. `php install.php` (или открыть `/install.php` в браузере) — создаёт базу и таблицы.

## Экран авторизации

Одна страница авторизации: одно поле «Мастер-пароль», логина нет.
Этот пароль — он же ключ авторизации (bcrypt-верификатор в БД) и ключ шифрования записей.
Если мастер-пароль в базе ещё не задан (первый запуск), кнопка становится
«Создать мастер-пароль» и создаёт единственную запись в таблице `users`.


## Шифрование

- Мастер-пароль пользователя — он же ключ авторизации и ключ расшифровки.
- В БД хранится только bcrypt-верификатор `password_hash(hash('sha256', password))`
  (сам пароль не хранится нигде).
- `login`, `password` и `comment` каждой записи шифруются на клиенте:
  ключ = `PBKDF2-SHA256(мастер-пароль, kdf_salt из таблицы users, 100000 итераций)`,
  шифрование `AES-256-GCM`, в БД лежит base64 строка `iv + ciphertext + tag`.
- Сервер ключ не хранит и ничего расшифровать не может: `api.php` отдаёт только шифротекст,
  расшифровку делает браузер тем же мастер-паролем.
- Число итераций задаётся в `config.php` (`kdf_iterations`) и должно совпадать
  с константой `ITERATIONS` в `assets/app.js`.

## Офлайн-режим

- `sw.js` кэширует `index.htm`, `app.css`, `app.js` по схеме cache-first с фоновым обновлением:
  файл из кэша отдаётся сразу (стили и скрипт доступны офлайн), свежая версия скачивается фоном
  и кладётся в кэш; при ошибке сети кэш не меняется и не очищается. Если файла в кэше нет и сети
  нет — отдаётся честный 503 (вместо файла HTML не отдаётся). Старые кэши удаляются только по
  имени `pm-shell-*`. Когда сеть есть, приложение шлёт SW сообщение `sync-shell`.
- `api.php` не кэшируется: запросы без сети падают, приложение детектирует ошибку и переходит на кэш.
- Офлайн определяется тремя способами: `navigator.onLine === false` (включая режим Offline в DevTools),
  падение `fetch` (`TypeError`) и таймаут 8 с без ответа (`AbortController`); ответы HTTP 500/503 и не-JSON
  тоже считаются потерей связи. События `online`/`offline` на `window` пересчитывают режим и экран
  авторизации: после возврата сети подсказка про кэш скрывается, кнопка снова «Разблокировать»,
  данные перезагружаются с сервера.
- В IndexedDB (`passmanager_cache`) хранятся:
  - `meta` — `kdf_salt`, «проба» (текст, зашифрованный ключом последнего входа) и время последнего входа;
    ни ключ, ни мастер-пароль в кэш не попадают;
  - `categories` — список категорий;
  - `entries:<id>` — шифротекты записей категории и время синхронизации.
- Без сети: вход по тому же мастер-паролю — ключ выводится локально и проверяется расшифровкой
  «пробы» (неверный пароль → AES-GCM бросает ошибку тега); категории и записи последней
  категории расшифровываются из кэша тем же ключом.
- В офлайн-режиме доступны только чтение, поиск, показ и копирование паролей;
  добавление и изменение записей и категорий заблокированы, сервер недоступен.
- Кнопка «Заблокировать» убирает ключ из памяти; данные в БД остаются зашифрованными.

## API (`api.php?action=...`)

| действие | метод | что делает |
| --- | --- | --- |
| `ping` | GET | проверка доступности сервера + нужен ли первый запуск (`setup_needed`) |
| `setup` | POST | первый запуск: создать единственный мастер-пароль, вернуть `kdf_salt` и `csrf` |
| `unlock` | POST | разблокировка: только мастер-пароль (поля «логин» нет), открыть сессию |
| `logout` | POST | закрыть сессию |
| `whoami` | GET | активна ли сессия |
| `categories` | GET | список категорий и число записей в них |
| `category_add` / `category_rename` / `category_delete` | POST | категории (удаление категории удаляет и её записи) |
| `entries` | GET | шифротекты записей категории |
| `entry_save` | POST | создать или обновить запись (шифротекты присылает клиент) |
| `entry_delete` | POST | удалить запись |

POST-запросы проверяют CSRF-токен сессии (заголовок `X-CSRF`).

## Ограничения и безопасность

- Одна сессия: после блокировки нужен повторный ввод мастер-пароля.
- Неудачные попытки разблокировки считаются в сессии (после 8 — ответ 429) и каждая
  неудачная попытка делает паузу 200 мс.
- Офлайн-доступ к данным последних записей означает, что в браузере лежат шифротекты
  и соль KDF: тот, кто имеет доступ к профилю браузера, может перебирать мастер-пароль офлайн.
  Это обычный риск локального хранилища.
- SHA-256 используется как пред-хеширование пароля, чтобы bcrypt не обрезал пароль по 72 байту.
- WebCrypto (`crypto.subtle`) работает только в secure context: `https://` или `localhost`.
  На `http://192.168.x.x` включите HTTPS или запускайте сервер как `localhost`.
- Кэшированные шифротекты бесполезны без мастер-пароля; сама БД без пароля не даёт доступных данных.
